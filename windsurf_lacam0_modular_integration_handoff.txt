What was already done
=====================
Phase 1 of the previous architecture was implemented.
The system is no longer just an offline request/response playback model.
The goal is now a live/lifelong simulation architecture where the simulation can keep running hypothetically forever unless the user manually stops it or configures an optional timestep limit.

An additional important change was also implemented:
The system now runs by PACE.
This means the user does not directly configure an exact fixed number of cars that will enter or leave.
Instead, the user configures:
- the pace/rate at which cars enter the parking lot
- the pace/rate at which cars leave the parking lot
- how many cars are initially in the parking lot

Important note:
There can be more total agents over the lifetime of the simulation than the number of agents visible at timestep 0.
The simulation is lifelong/dynamic, so new agents may appear later according to the entry pace, and parked agents may later decide to exit according to the exit pace.

Current goal
============
I want to integrate LaCAM0 as a selectable algorithm.
When the user selects LaCAM0, the system should use LaCAM0 for path planning.
When the user selects Priority Planner, the existing priority planner should continue working and should not be broken.

This is important because in the future I want to compare algorithms and maybe add more algorithms.
So the design should be modular and extensible.

Critical design point
=====================
Priority Planner and LaCAM0 are conceptually different.

Priority Planner:
- Plans cars individually / in priority order.
- Uses the ReservationTable for space-time reservations.
- Fits the current existing architecture more naturally.

LaCAM0:
- Is a MAPF solver.
- Solves a batch MAPF problem with multiple active agents together.
- Does not use the existing ReservationTable in the same way.
- Requires MAPF benchmark-style files:
  - .map file, representing the grid
  - .scen file, representing active agents with start/goal positions
  - result file, representing positions per timestep
- Therefore it may require a different simulation/planning flow than Priority Planner.

Please do not force LaCAM0 into the same exact interface if that creates bad design.
Instead, design the correct abstraction.

Important architecture question
===============================
The hardest class to adapt may be SimulationCore.
The current SimulationCore may be too tied to the existing Priority Planner / ReservationTable style.

Please think carefully about whether the right design is:
1. One SimulationCore with pluggable strategy objects,
2. A base simulation engine with algorithm-specific simulation cores,
3. A SimulationCoreFactory that creates PrioritySimulationCore vs LacamSimulationCore,
4. A PlannerManager/ExecutionManager split,
5. Or another design you think is better.

I am open to your recommendation.
Do not just follow my suggestions blindly.
Design based on what is correct, maintainable, and modular.

Expected design goals
=====================
The new architecture should:

1. Preserve existing Priority Planner behavior.
   - Priority Planner should continue working as before.
   - Do not break the current reservation-table based logic.

2. Add LaCAM0 as an alternative planner.
   - User selects algorithm in the frontend.
   - Backend creates the correct simulation/planning components based on the selected algorithm.

3. Keep future algorithm comparison possible.
   - The design should make it possible to add more planners later.
   - Avoid hardcoding LaCAM0 deeply into SimulationCore if possible.

4. Support lifelong simulation.
   - Simulation may run indefinitely.
   - max_timesteps is optional, not mandatory.
   - Entry and exit are based on pace/rates.
   - There may be new cars added over time.
   - Parked cars may later become active and leave.

5. Handle LaCAM0 correctly.
   - LaCAM0 should plan active moving agents as a MAPF batch.
   - Inactive parked cars should likely be treated as static obstacles in the .map.
   - Active cars should be represented as agents in the .scen file.
   - LaCAM0 result should be parsed and converted back into the internal car path/state representation.
   - LaCAM0 does not need the ReservationTable in the same way Priority Planner does.

6. Avoid unnecessary global replanning every timestep.
   - Use event-driven replanning or rolling horizon if appropriate.
   - Replan when cars enter, cars request exit, paths expire, or a configured replan interval is reached.
   - The exact policy should be designed carefully.

7. Keep frontend/backend communication compatible with Phase 1.
   - WebSocket live updates should remain the main communication method.
   - Frontend should not know the internal details of LaCAM0.
   - Frontend receives car positions/status/stats in the same general STEP message structure regardless of algorithm.
