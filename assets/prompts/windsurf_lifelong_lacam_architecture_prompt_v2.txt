What I want to change

I want to redesign the system into a lifelong simulation.

By lifelong, I mean the simulation can hypothetically run forever. It should not be based on “run simulation -> calculate everything -> return full JSON -> display.” Instead, the simulation should run timestep by timestep and keep updating.

The user may optionally configure a maximum number of timesteps. If a max timestep limit is provided, the simulation stops when it reaches that limit. If no max timestep limit is provided, the simulation can continue running until the user stops it manually.

The user should also be able to configure the pace/rate at which cars enter and leave the parking lot. Entering cars and exiting cars should each have their own configurable rate/pace. For example, the user may configure cars to enter frequently but leave rarely, or the opposite.

The new desired conceptual flow is:

1. Frontend sends simulation configuration.
2. Backend initializes the simulation state.
3. Backend starts a timestep loop.
4. At each timestep:
   - Existing active cars move according to planned paths.
   - New cars may enter based on the configured entrance rate.
   - Parked cars may decide/request to leave based on the configured exit rate.
   - The backend updates the simulation state.
   - The backend may call the MAPF planner when new planning/replanning is needed.
   - The backend sends the current timestep/state update to the frontend.
5. The frontend displays the simulation live as updates arrive.
6. The simulation continues until the user stops it or until the optional timestep limit is reached.

LaCAM0 integration

I want to replace or extend the current priority planner with LaCAM0.

LaCAM0 is a MAPF planner. It solves Multi-Agent Path Finding problems. It is not the whole simulation engine. It should be used as a planner that receives a MAPF problem snapshot and returns paths.

LaCAM0 knows how to handle benchmark-style MAPF problems. Therefore, to use it, the backend needs to generate benchmark-style files:

1. A .map file
   - This represents the grid/map.
   - Walkable/drivable cells should be represented as free cells.
   - Obstacles, walls, blocked cells, and possibly parked inactive cars should be represented as blocked cells.

2. A .scen file
   - This represents the agents.
   - Each active moving car should become one MAPF agent.
   - Each agent needs a start position and a goal position.
   - Starts should come from the car’s current position.
   - Goals should come from the car’s current target, such as assigned parking spot, exit, or another intermediate goal.

3. A result/output file
   - LaCAM0 writes the planned paths into a result file.
   - The backend needs to parse this file and convert it into the simulation’s internal path format.

Important design point:

LaCAM0 should not control the entire simulation. The SimulationCore should control the timestep loop and global simulation state. LaCAM0 should only be called when path planning or replanning is needed.

Possible planning approach:

- Active moving cars should be sent to LaCAM0 as agents.
- Parked/inactive cars should usually not be sent as agents. They should usually be treated as obstacles in the .map.
- The system should avoid calling LaCAM0 for every single timestep if not needed.
- Replanning can happen when:
  - A new car enters.
  - A parked car wants to exit.
  - A car reaches its current goal.
  - A path becomes invalid or blocked.
  - A periodic replanning interval is reached.
- The system can use a rolling-horizon approach: plan ahead for a limited window, execute some steps, then re-evaluate.

Important architecture goal

Please design the system so the planner can be swapped cleanly.

For example, it would be good to have something like:

- Planner interface / base class
