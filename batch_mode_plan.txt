1. CURRENT ARCHITECTURE SCAN
--------------------------------------------------------------------------------

FRONTEND FLOW (current):
  Home (/)
    → "Start Simulation" → links directly to /config
  SimulationConfig (/config)
    → saves config to sessionStorage["sim_config_v3"]
    → navigates to /layout
  Layout (/layout)
    → user picks/generates a parking lot
    → navigates to /simulation?layout=<id>
  Simulation (/simulation)
    → reads sessionStorage config
    → if headless_mode → POST /simulation/headless, shows headlessResult panel
    → if comparison_mode → POST /simulation/compare, shows comparisonResults panel
    → otherwise → POST /simulation/start + WebSocket live view

ROUTES (router.tsx):
  /                → Home
  /config          → SimulationConfig
  /layout          → Layout
  /layout/new      → CreateParkingLot
  /layouts         → SavedLayouts
  /simulation      → Simulation
  /editor          → Editor
  /stats           → Stats
  /about           → About

KEY BACKEND ENDPOINTS:
  POST /simulation/start     → live simulation (WebSocket)
  POST /simulation/headless  → request: HeadlessSimulationRequest
                               response: HeadlessResultDTO
  POST /simulation/compare   → request: ComparisonRequest (algorithms list)
                               response: ComparisonResultDTO (list of HeadlessResultDTO)

HeadlessSimulationRequest fields:
  source, width, height, rules, parkingLotId
  planning_horizon, goal_reserve_horizon, arrival_lambda, exit_rate
  initial_cars, max_arriving_cars, algorithm, max_steps

HeadlessResultDTO fields (the stats object):
  mode, algorithm, max_steps, completed_steps, stopped_reason, status
  grid_width, grid_height, parking_lot_id
  initial_cars_configured, max_arriving_cars_configured
  total_cars, total_parked, total_failed_plans, total_exited
  arriving_cars_spawned, arriving_cars_parked
  average_steps_to_park, average_steps_to_exit
  avg_trip_duration_steps, max_trip_duration_steps, min_trip_duration_steps,
  total_completed_trips
  avg_planner_ms, max_planner_ms, planner_call_count
  cpu_usage_avg_percent, cpu_usage_peak_percent
  memory_usage_avg_mb, memory_usage_peak_mb
  machine_specs

SimulationConfig TS type:
  planning_horizon, goal_reserve_horizon, arrival_lambda, exit_rate,
  initial_cars, max_timesteps, step_delay_ms, algorithm,
  headless_mode, comparison_mode, comparison_algorithms

NOTE: step_delay_ms, headless_mode, comparison_mode, comparison_algorithms are
      frontend-only fields (not in HeadlessSimulationRequest).

--- 2b. New Batch Config page ---

Route:  /batch-config
File:   frontend/src/pages/BatchSimulationConfig.tsx
Style:  frontend/src/pages/BatchSimulationConfig.css

The page contains a list of simulation config "blocks":
  - Starts with 1 block.
  - Each block is labeled "Simulation 1", "Simulation 2", etc.
  - Each block has the same fields as SimulationConfig EXCEPT:
      EXCLUDED: headless_mode (always true internally)
      EXCLUDED: step_delay_ms (irrelevant for headless)
      EXCLUDED: comparison_mode
      EXCLUDED: comparison_algorithms
      INCLUDED: max_timesteps (required ≥ 1 for headless; validated)
  - Each block has a ✕ "Delete" button (disabled when only 1 block remains).
  - Below all blocks: "＋ Add Simulation" button (disabled at 20 blocks).
  - At the bottom: "Run Batch" button.

Shared config fields per block (TypeScript type: BatchSimEntry):
  {
    id: string (uuid, client-side only),
    algorithm: string,
    planning_horizon: number,
    goal_reserve_horizon: number,
    arrival_lambda: number,
    exit_rate: number,
    initial_cars: number,
    max_arriving_cars: number,
    max_timesteps: number,    ← required ≥ 1
    source: "generate" | "load",
    layout_id?: string,        ← picked from a layout selector or the shared layout
  }

LAYOUT STRATEGY for batch mode:
  All batch simulations share the same parking lot layout (chosen before
  running). This mirrors comparison mode's approach and avoids a complex
  per-simulation layout picker.
  Flow: /batch-config → user configures N sims → clicks "Choose Layout & Run"
        → navigates to /layout?batch=1 (passing flag indicating batch mode)
        → Layout page detects batch flag → "Start Simulation" →
          navigates to /batch-results (new results page)

  OR (simpler, preferred): batch-config page includes an inline "layout source"
  section (generate or load from saved) so the user picks layout once for
  all simulations on the same screen.

PREFERRED APPROACH: Keep /batch-config self-contained with a layout source
section. No need to navigate through /layout for batch mode.

--- 2c. Batch Results page ---

Route:   /batch-results (rendered inline on /batch-config after run, OR separate page)
Preferred: Show results inline on the batch-config page (replace the config blocks
           with results after run completes). This avoids navigation state issues.

Results layout:
  - Summary banner: "Batch Complete — N/M simulations successful"
  - Per-simulation result cards (or table), each showing:
      Header: "Simulation N" · algorithm badge · status badge
      Stats grid (same stat cards as the headless panel in Simulation.tsx):
        Exited, Arrivals Parked, Failures, Avg Trip, Trip Range,
        Avg Planner ms, CPU, Memory
  - "Run Again" button (goes back to config state)
  - "Export to CSV" button (optional, nice to have)

Per-simulation execution state (shown during run):
  Each block transitions through states:
    ⟳ pending  →  ⏳ running  →  ✓ success  |  ✗ failed
  This is possible because the frontend calls /simulation/headless N times
  sequentially — see Section 3.

--- 2d. Reuse strategy for config fields ---

The config form fields from SimulationConfig.tsx will be extracted into a
small reusable component: SingleSimConfigForm (or inline hook).

Approach: Extract the FieldRow/SelectRow/ToggleRow field groups into a
  shared functional component that takes:
    props: { config: BatchSimEntry, onChange: (field, value) => void }
  This component is used both in SimulationConfig.tsx and
  in each block of BatchSimulationConfig.tsx.

  Alternatively (simpler, less refactor risk): simply duplicate the field
  JSX inside BatchSimulationConfig since SimulationConfig.tsx already has
  comparison/headless toggles that batch mode must not show anyway.
  This is safer and avoids touching the working SimulationConfig.tsx.

DECISION: Duplicate fields in BatchSimulationConfig to avoid touching
  the existing SimulationConfig.tsx at all. Risk of UI divergence is low
  since the batch config UI is intentionally simpler.

3. BACKEND DESIGN
--------------------------------------------------------------------------------

--- 3a. Execution strategy: Frontend-orchestrated sequential calls ---

RECOMMENDATION: Do NOT add a new backend batch endpoint.
Instead, the frontend calls POST /simulation/headless N times in sequence.

Rationale:
  1. Per-simulation progress (running/done/error) is naturally shown as each
     call completes — no SSE or streaming needed.
  2. No risk of HTTP timeout on a long-running batch.
  3. No new backend code to test or maintain.
  4. Each call is fully independent (no shared state, no parallel mutations).
  5. The backend already handles all algorithms including LNS2/LaCAM0.
  6. One failed simulation does NOT affect the others.

Sequential execution pseudocode (frontend):
  for (const sim of batchSims) {
    setSimStatus(sim.id, "running");
    try {
      const result = await fetch("/simulation/headless", { body: buildRequest(sim, layout) });
      setSimResult(sim.id, await result.json());
      setSimStatus(sim.id, "success");
    } catch (err) {
      setSimStatus(sim.id, "failed");
      setSimError(sim.id, err.message);
    }
  }

OPTIONAL backend batch endpoint (Phase 2, after approval):
  POST /simulation/batch
  Request:  BatchSimulationRequest { simulations: List[HeadlessSimulationRequest] }
  Response: BatchResultDTO { results: List[BatchSimResultItemDTO] }

  BatchSimResultItemDTO:
    index: int
    status: "success" | "failed"
    algorithm: str
    max_steps: int
    result?: HeadlessResultDTO
    error?: str

  This would be a thin wrapper that loops over simulations and calls
  _build_and_run_headless() for each, catching exceptions per-simulation.
  Run sequentially (not parallel) to avoid concurrent mutable state in
  simulation cores.

  For now, the frontend-sequential approach is used. The batch endpoint
  can be added in Phase 2 if backend orchestration is preferred.

4. DTO DESIGN
--------------------------------------------------------------------------------

No new DTOs are needed for Phase 1 (frontend-sequential approach).
The existing HeadlessSimulationRequest and HeadlessResultDTO are reused.

Frontend-only type:
  type BatchSimEntry = {
    id: string;                  // client uuid
    algorithm: string;
    planning_horizon: number;
    goal_reserve_horizon: number;
    arrival_lambda: number;
    exit_rate: number;
    initial_cars: number;
    max_arriving_cars: number;
    max_timesteps: number;       // required ≥ 1 for headless
  }

  type BatchSimStatus = "pending" | "running" | "success" | "failed";

  type BatchSimState = {
    entry: BatchSimEntry;
    status: BatchSimStatus;
    result?: HeadlessResult;     // HeadlessResultDTO equivalent
    error?: string;
  }

If backend batch endpoint is added (Phase 2):
  class BatchSimulationRequest(BaseModel):
    simulations: List[HeadlessSimulationRequest]   # max 20

  class BatchSimResultItemDTO(BaseModel):
    index: int
    status: Literal["success", "failed"]
    algorithm: str
    max_steps: int
    result: Optional[HeadlessResultDTO] = None
    error: Optional[str] = None

  class BatchResultDTO(BaseModel):
    results: List[BatchSimResultItemDTO]


--------------------------------------------------------------------------------
5. SOLVER INTEGRATION
--------------------------------------------------------------------------------

Batch mode uses exactly the same backend flow as single headless mode:
  _build_and_run_headless() is called for each simulation.
  Each call creates fresh instances of:
    Grid, ParkingManager, GhostExitManager (for lacam0/lns2),
    SimulationCore / LaCAM0SimulationCore / LNS2SimulationCore.
  Zero shared state between batch simulations.
  Supports: priority, lacam0, lns2 — all currently working algorithms.
